# D8-4: 结果分析与 false positive 识别

> 时长：约 25 min ｜ 凭证：D8-2 或 D8-3 的产物 ｜ 类型：评审

## 背景
红队工具会把一些**无害响应**也标成"攻击成功"——这就是 false positive。如果不做人工 review 直接把 ASR 报给 PM，会出现两种灾难：
- 数字虚高，团队疲于追假问题
- 真问题被误判淹没，反而漏

本子任务是 D8 的收口：把 baseline 数字翻译成"修 / 不修 / 加 system prompt 兜底"的可执行决策。

## 你需要做什么
1. 把 baseline 报告里的攻击 case 按类型分桶（至少 2-3 类）
2. 挑出 **Top 3 失败 case** 做人工 review，每个 case 写：
   - 工具判定（成功 / 失败 / 部分）
   - 你的判定（真问题 / false positive / 边界情况）
   - 处置决策（修代码 / 加 system prompt 兜底 / 不修 + 理由 / 升级到 D9 runbook）
3. 识别 **≥ 1 个 false positive 类型**，写清楚：
   - 这个类型为什么容易被工具误判（如：礼貌拒绝被识别为"配合攻击"）
   - 后续 baseline 怎么处理（过滤 / 调权 / 在报告里另列）
4. 把"修"和"加兜底"的 case 转成 D9 CI/CD gate 设计的输入（gate A 阈值参考）

## 提示
- false positive 的常见来源讲师手册 D8 有清单，听讲师举例
- "不修"的决策必须有理由，"以后再说"不算（讲师手册反例 #3、验收 checklist 末条）
- 别陷入逐条 case 抠字眼——Top 3 就够，时间花在判定逻辑上

## 自检
- [ ] Top 3 case 每条都有：工具判定 / 个人判定 / 处置决策 / 理由
- [ ] 至少 1 个 false positive 类型已识别并说清误判原因
- [ ] 能口头说出"业务可接受 ASR 上限是 X%，本次 baseline 是 Y%，差距如何处理"

## 提交（计入综合作业）
- Top 3 case review 表（Markdown 表格即可）
- false positive 类型清单（≥ 1 类，含误判原因）
- 一句话决策："本 agent 当前是否可以进入 D9 CI/CD gate 设计"

## 反例
- ASR=0% 才算过：不现实（讲师手册反例 #1）
- 把工具判定的"成功"全当真问题：没做人工 review（反例 #2）
- 把红队跑完就归档：红队是 gate，模型/prompt/工具变了都要重跑（反例 #3）
