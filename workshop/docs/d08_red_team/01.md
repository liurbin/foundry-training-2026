# D8-1: Portal 红队 baseline 观看

> 时长：约 20 min ｜ 凭证：仅看讲师演示，无需 Azure ｜ 类型：讲

## 背景
红队（Red Team）在 Foundry 里是"上线门槛"，不是一次性的合规活动。Day 2 下午这一段先让你看一遍 Portal 端到端怎么跑——主要是为了：
- 知道 `num_objectives` 是什么、为什么从 3 起步
- 看清 portal 报告里 ASR（Attack Success Rate）摆在哪、按攻击类型怎么分桶
- 理解后续 SDK 跑的结果应当和 portal 在同一量级（差 ≤ 2x 算合理）

本子任务**不要求每人当场跑 portal**，因为单次 baseline 耗时长，全员并发会卡。

## 你需要做什么
1. 跟着讲师投屏，看完一次完整 portal 红队流程：
   - 选被测 agent（D3 单 agent 或 D6a/D6b 替代）
   - 配置 attack set，`num_objectives=3`
   - 触发 baseline，等结果
   - 打开报告页，读 ASR、攻击类型分类、Top 失败 case
2. 在自己笔记里抄下三件事：
   - 这个 agent 的 ASR 数字（讲师当场跑的）
   - portal 报告里出现的攻击类型有哪几类
   - 一个让你觉得"这个判定不太对吧"的 case（哪怕只是直觉）

## 提示
- ASR = 攻击成功率，工具自动判定"成功"的比例。不是越低越好的纯指标——某些攻击类型本身就容易被工具误判（false positive）
- `num_objectives` 越大跑得越久；课堂上不要鼓动讲师调大
- portal 报告里的"成功"≠"真出事"，要带着怀疑读

## 自检
- [ ] 能口头说出讲师跑的那个 agent 的 ASR 数字
- [ ] 能说出报告里至少 2 个攻击类型名字
- [ ] 能在 portal 报告页指出 ASR、攻击分类、case 列表分别在哪个区域

## 提交（计入综合作业）
- 笔记里记下：演示 ASR 数字 + 攻击类型清单 + 1 个你怀疑是误判的 case 描述（这个 case 在 D8-4 还会用到）

## 反例
- 跟着看完就走，没记数字：D8-2 SDK 跑完没法做量级对比
- 把 portal 的"成功"直接当真问题数：跳过了人工 review 这一步（讲师手册 D8 反例 #2）
