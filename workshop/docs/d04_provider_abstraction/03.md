# D4-3: Foundry ↔ 非 Azure provider live switch 观看

> 时长：约 20 min ｜ 凭证：无（讲师持非 Azure key，学员不发不传）｜ 类型：讲师演示 + 学员观察记录

## 背景
- 学员侧不持任何非 Azure provider key，这步是讲师在 portal 之外 live 切换演示
- 你的任务是**观察差异点**并记录，回答"我项目 1 年内会不会真换 provider"
- abstraction 课不应该被 key 卡住——这是刻意设计

## 你需要做什么
1. 讲师会在共享屏幕上做 3 件事：
   - 改一个 env (`PROVIDER=foundry` → `PROVIDER=anthropic` 或 openai-direct)
   - 不改业务代码，重跑一次
   - 把两次返回放一起对照
2. 你的任务：在自己笔记里记录至少 **2 个差异点**，候选维度：
   - 响应格式（字段名 / 结构）
   - 错误码（429 / 5xx / 鉴权失败的 status code）
   - 配额行为（rate limit window 长短）
   - 工具调用语义（tool_choice / function name 规范）
3. 回答 D4 最终决策问题：

   ```markdown
   # D4 决策记录

   ## 我这个项目 1 年内会不会真的换 provider？
   [会 / 不会 / 不确定]

   ## 这层抽象值不值得加？
   [值 / 不值，理由]

   ## live switch 观察到的差异点
   1. ...
   2. ...
   ```

## 提示
- 学员**不要**自己配非 Azure key 跑；如课后想试，自付费自配
- 差异点不一定多，2 个能讲清楚比 5 个泛泛而谈强
- "不值得加"是合法答案；如果你项目 1 年内不会换，抽象就是欠债

## 自检
- [ ] 记录 ≥2 个 Foundry vs 非 Azure provider 差异点
- [ ] 给出"会/不会换 provider"的明确判断
- [ ] 给出"这层抽象值不值"的结论 + 理由
- [ ] 业务代码（grep）没有任何具体 provider 名

## 提交（计入综合作业）
- 产物：`decision.md`（含上面三段）
- 放：`submissions/d4_3_switch/decision.md`

## 反例
- 不记差异点直接抄讲师 PPT —— 等于没看
- 结论"为了灵活性所以值得" —— 灵活是修辞，要给 1 年内换 provider 的具体场景
- 因为讲师没让你跑就觉得"我用不上抽象" —— 综合作业仍按"是否需要抽象"评分
