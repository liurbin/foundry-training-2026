# D5-2: 缓存策略与雷区

> 时长：约 25 min ｜ 凭证：无（本地缓存即可）｜ 类型：实操 + 设计

## 背景
- 在 provider 层加一层 prompt+model 命中缓存，目的是降模型费 + 降 p95 延迟
- 缓存键设计是雷区：**键不准包含 user_id / 个人数据** —— 既是合规问题，也会让命中率失真
- TTL 不是越长越好，模型/提示词变动时陈旧缓存是污染源

## 你需要做什么
1. 在 provider 层加一层缓存（内存 dict 或 Redis 都行；MVP 用内存）：

   ```python
   import hashlib, json, time

   def cache_key(messages, model, common_opts):
       # 只放 prompt 内容 + model + 共性 opts 哈希
       payload = json.dumps({
           "messages": [{"role": m.role, "content": m.content} for m in messages],
           "model": model,
           "opts": common_opts,
       }, sort_keys=True)
       return hashlib.sha256(payload.encode()).hexdigest()
   ```

2. **键里禁止出现**：`user_id` / email / IP / session_id / 任何 PII —— 写在代码注释里
3. 选 TTL 并在代码里写一段注释解释**为什么是这个值**，候选维度：
   - 提示词多久会调一次
   - 模型版本多久切一次
   - 业务能容忍多旧的回答
4. 加命中率统计：每次 `chat()` 记录 hit/miss，跑一段后能算出命中率
5. 跑一遍 D4 的业务测试，确认：
   - 同样请求第二次返回时间显著降低
   - 命中率 > 0

## 提示
- TTL 写得太短（如 1min）命中率上不去；写得太长（如 7d）模型升级后陈旧
- 内存缓存进程重启就丢，MVP OK；上线要换成共享缓存
- 命中率 = hit / (hit + miss)；这个数字 D5-3 成本估算会用到

## 自检
- [ ] cache_key 计算函数里没有 user_id / email / IP / 任何 PII —— grep 抽查
- [ ] TTL 选择有书面理由（不接受"我觉得 1 小时差不多"）
- [ ] 命中率统计能打印出真实数字（不是"应该会命中"）
- [ ] 能口头讲清"为什么键里不能含 user_id"（答：合规雷区 + 命中率失真）

## 提交（计入综合作业）
- 产物：`providers/_cache.py` + 一段命中率日志 + TTL 决策注释
- 放：`submissions/d5_2_cache/`

## 反例
- 缓存键直接用整个 prompt 字符串 —— 一个空格差异就 miss，且 PII 写进缓存 store
- 键含 user_id "为了用户隔离" —— 同一 prompt 不同用户必 miss，等于没缓存 + 合规风险
- TTL 写"30 天" 没理由 —— 模型/提示词改一次缓存就全错
- 命中率写"应该会命中"没数字 —— 验收硬性不接受
