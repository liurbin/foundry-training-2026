# D6a-3: 决策卡填写 + 成本净差额

> 时长：约 15 min ｜ 凭证：无（成本估算用 D5 表） ｜ 类型：评审

## 背景

前两步给了你"两条路径都跑通 + 客观差异表"。本步把它收敛成一张"何时从 Agent Service 切到 SDK"决策卡，关键是 4 个触发条件 + 我项目命中几条 + 成本净差额方向。不许停在"代码更优雅"。

## 你需要做什么

1. 复制下面 4 个触发条件，逐条勾选你项目命中没有：
   - [ ] Agent Service 不支持我要的编排模式（如自定义状态机）
   - [ ] 我需要把 agent 嵌入已有服务进程（不想多一个托管运行时）
   - [ ] 我对延迟敏感，托管层多一跳无法接受
   - [ ] 我要的 provider 不在 Foundry 模型目录里
2. 命中 ≥ 1 条 → 考虑 SDK；命中 0 条 → 留在 Agent Service。结论必须与命中条数一致。
3. 填成本影响栏（SDK 相比 Service 新增的成本项）：
   - 运行时：Container Apps / VM 实例费（参考 D5 估算表）
   - 观测：自接 Application Insights 摄入费 + dashboard 维护
   - on-call：24/7 还是工作时间？谁轮值？
   - 状态：自建状态存储（Redis / Cosmos）
4. 写一句"省下的托管费 vs 上述新增项，净差额方向：正 / 负 / 不确定 + 一句理由"。
5. 如果你最终决定两条路径都保留：在 README 写清业务理由（不接受"以防万一"）。

## 提示

- "命中 0 条但我还是想切 SDK 因为代码更优雅" → 这就是 D6a 反例 1，砍掉。
- 净差额"不确定"是合法答案，但要写"我缺什么数据才能算清"。
- on-call 这一格容易空——团队没人值班就老实写"无 on-call 能力，不能选 SDK"。

## 自检

- [ ] 4 个触发条件逐条勾选完
- [ ] 最终选择（Service / SDK / 两条都留）与命中条数一致
- [ ] 成本影响 4 项（运行时 / 观测 / on-call / 状态）都填了，不空
- [ ] 净差额方向有明确"正 / 负 / 不确定"+ 一句理由
- [ ] 若两条都留，README 写清业务理由（不是"以防万一"）
- [ ] 能口头讲清"我项目 6 个月内会不会从 Service 切 SDK"

## 提交（计入综合作业）

- 决策卡文件（Markdown）
- 若两条路径都保留：README 中的业务理由段落

## 反例

- "SDK 代码更少更优雅所以切 SDK" → 代码量不是切换理由
- 命中 0 条还是选 SDK → 与决策卡逻辑矛盾，重填
- 成本影响栏全留空或写"略" → 直接判负
- "两条都跑通所以都保留" → 没业务理由就砍一条
