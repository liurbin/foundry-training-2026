# D5-1: 429 Retry with Jitter / D5-1: 429 retry + jitter

> 时长：约 25 min ｜ 凭证：无（用 stub 注入 429，不依赖真实配额）｜ 类型：实操

## Background / 背景
- D3 你只在业务层"捕获 + 打日志"，本步在 provider/HTTP 客户端层加重试
- 重试必须有 jitter，否则多副本同时退避会 thundering herd
- 禁止业务层 catch-retry —— 那是 negative example #2
- stub 脚本放在 `workshop/code/stub_429/`（由另一 agent 同期产出）

## What You Need to Do / 你需要做什么
1. 在 D4 的 provider 层（不是业务层）加一个重试 wrapper：

   ```python
   import asyncio, random

   async def with_retry(call, max_attempts=3, base=0.5, cap=4.0):
       for attempt in range(max_attempts):
           try:
               return await call()
           except RateLimitError as e:  # 429
               if attempt == max_attempts - 1:
                   raise
               delay = min(cap, base * (2 ** attempt)) * (0.5 + random.random())
               await asyncio.sleep(delay)
           except ServerError:  # 5xx
               if attempt == max_attempts - 1:
                   raise
               await asyncio.sleep(min(cap, base * (2 ** attempt)))
   ```

2. 把 wrapper 套到 `FoundryProvider.chat()` 的实际网络调用
3. 跑 stub server + 通过 retry_client 调用（参考 `workshop/code/stub_429/`）：

   ```bash
   # 终端 A：起 stub（前 3 次返回 429，第 4 次成功）
   python workshop/code/stub_429/stub_server.py --port 18429 --fail-times 3

   # 终端 B：用带 retry 的客户端调用
   python workshop/code/stub_429/retry_client.py --url http://127.0.0.1:18429/
   ```

4. 观测：日志里能看到 attempt 1/2/3 的退避间隔，且**间隔有随机性**（jitter 生效）
5. 业务层不应该看到 429 异常 —— 要么成功要么最终抛业务可见的错误

## Tips / 提示
- 退避上限别忘了（cap=4s 之类）；指数退避无 cap 会一次睡 10 分钟
- jitter 不是 sleep 整数秒后加 ±0.1s；要在退避基数上乘 0.5-1.5 的随机
- 不要在业务层 try/except 429 —— 多处重复 + 没 jitter

## Self-Check / 自检
- [ ] 重试代码在 provider 层一处（grep "retry" 不散落 5+ 文件）
- [ ] stub 注入 429 时业务流程能恢复，不抛到业务层
- [ ] 日志能看出 attempt N 的退避间隔有 jitter
- [ ] 重试上限明确写死（默认 3）

## Negative Examples / 反例
- 重试逻辑写在业务层 —— 多处重复 + thundering herd
- 无 jitter 的纯指数退避 —— 多副本同步重试
- 无上限重试 —— 一次故障变成 30 分钟雪崩
- 把 5xx 和 429 用同一退避参数 —— 配额漂移和服务故障语义不同
