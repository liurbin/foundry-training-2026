# D5-02: Cache Strategy and Pitfalls

> Module: D5 Deployment, Capacity, Scaling, and Cost | Credentials: Learners use stubs and replay responses; instructor owns real load tests

## Purpose
Define a cache key, TTL, and privacy exclusions. This step turns the module decision into a concrete learner artifact that can be reviewed during class.

## Instructions
- Define a prompt plus model cache key that excludes user identifiers and personal data.
- Pick a TTL and write the business reason for it.
- Show that at least one repeat request hits the cache.

## Acceptance Criteria
- The requested artifact exists and can be reviewed by the instructor or assistant.
- The artifact uses concrete values from your project rather than generic placeholders.
- Any uncertainty is written explicitly instead of hidden.
- The output remains consistent with earlier decision cards unless you document why the decision changed.

## Submission
- Save the artifact in the matching `submissions/` folder for this step.
- Include short notes, screenshots, logs, or trace links only when they prove the acceptance criteria.

## Common Mistakes
- Choosing PTU without current stable high-throughput SLA.
- Using user_id in a cache key.
- Running learner-side real load tests against shared quota.
