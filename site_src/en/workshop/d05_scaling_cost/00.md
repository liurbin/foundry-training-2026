# D5-0: 部署与容量模式对照（前置 15 min）

> 时长：约 15 min ｜ 凭证：无 ｜ 类型：讲 + 练（决策卡 + 提交物）

## Background / 背景
- 在你写一行 retry / cache / 成本脚本之前，先选清两件事：**agent 跑在哪**（部署目标）+ **token 配额怎么买**（容量模式）
- 这两件事是 D2 决策卡里"硬约束触发条件"栏的实操展开。D2 已经让你判定了"是否命中私有部署 / 高吞吐 SLA / 预算敏感"等条件，本步把维度的实际选项摊开
- 后续 D5-1/2/3 的所有产出（retry 策略 / 缓存命中率假设 / 成本三档）都依赖你在这一步选定的部署目标 + 容量模式

## What You Need to Do / 你需要做什么
1. 拷入 decision note 模板：

   ```markdown
   # D5 Deployment / Capacity Decision Note

   ## 上下文（从 D2 决策卡承接）
   - D2 命中的硬约束（私有部署 / 网络隔离 / 最少运维 / 高吞吐 SLA / 预算敏感）：[列命中项]
   - 业务流量预期：[日活 / QPS / 是否可预测]
   - SLA 承诺：[p95 延迟 / 月度可用率，若有]

   ## 部署目标选择（3 选 1）
   | 模式 | 选择 | 理由（≥1 句） |
   |------|------|-------------|
   | Foundry Hosted Agents（主路径） | [ ] | |
   | Container Apps 自托管 | [ ] | |
   | SDK self-host（AKS / App Service / VM） | [ ] | |

   **为什么不选其他两个**（每项 1 句）：
   - 不选 X：[…]
   - 不选 Y：[…]

   ## 容量模式选择（4 选 1，可叠加 Reservation）
   | 模式 | 选择 | 理由（≥1 句） |
   |------|------|-------------|
   | PAYG + 默认配额（主路径） | [ ] | |
   | Quota increase（PAYG 配额增配） | [ ] | |
   | PTU / Provisioned Throughput | [ ] | |
   | Reservation（可与 PTU 叠加） | [ ] | |

   **为什么不选其他**（每项 1 句）：
   - 不选 X：[…]
   - 不选 Y：[…]
   - 不选 Z：[…]

   ## 与 D2 一致性
   - D2 容量类硬约束（高吞吐 SLA / 预算敏感）是否已承接到本表？[是 / 否 + 说明]
   ```

2. 用下表帮你选——3 个部署目标，命中"何时选"那一格就选它：

   | 模式 | 何时选 | 学员要操心什么 |
   |------|-------|---------------|
   | **Foundry Hosted Agents**（主路径） | 默认选；除非命中下面两条 | 几乎不用操心，scale-to-zero 默认 |
   | Container Apps 自托管 | 必须自托管 / VNet 强约束 / 客户私有 Azure | min replicas、镜像、滚动升级 |
   | SDK self-host（AKS / App Service / VM） | 跨云 / 客户自带 K8s / 真私有部署 | 全套 K8s 运维 + 自接观测 |

3. 用下表选容量模式——可以叠加 Reservation：

   | 模式 | 何时选 | 备注 |
   |------|-------|------|
   | **PAYG + 默认配额**（主路径） | 默认；流量不可预测；POC / 中小规模 | 触发 429 → 加 retry + cache 即可，多数场景够用 |
   | Quota increase（PAYG 配额增配） | 流量上涨但仍有抖动；不想买 commitment | 走 [quota request form](https://aka.ms/oai/stuquotarequest)，区域 + 模型有上限 |
   | PTU / Provisioned Throughput | 高吞吐 + 稳定 SLA + 流量可预测 | 按月起买；区域 + 模型限制更窄 |
   | Reservation | 长期稳定用量 + 财务上要锁价 | commitment 期限 ≥ 1 年；和 PTU 正交 |

4. **每个"为什么不选"必须写 ≥1 句理由**——不接受"业务不需要"这种空话
5. 把 decision note 保存好，D5-3 成本估算会按这个 note 里的容量模式决定计费假设

## Tips / 提示
- 默认就是 Hosted Agents + PAYG —— 多数学员会选这两个，关键是写清"为什么不选其他"
- 命中"私有部署 / 网络隔离" → 必走自托管路径（ACA 或 SDK self-host），不能选 Hosted Agents
- "我们以后可能要 PTU" 不是选 PTU 的理由——选 PTU 要有当前的高吞吐 + SLA 数字
- 容量类硬约束在 D2 已经判定过了——这里只是把"D5 要 capacity planning"的结论落到具体一行

## Self-Check / 自检
- [ ] decision note 5 张表（部署目标 / 部署"不选"理由 / 容量模式 / 容量"不选"理由 / D2 一致性）全填，无空白
- [ ] 每个"为什么不选"都有 ≥1 句业务理由（不是"不需要"）
- [ ] D2 命中的容量类硬约束已在本 note 承接说明
- [ ] 部署目标和容量模式的选择能 1 句话讲给同桌听

## Negative Examples / 反例
- 4 张表选了 4 个 main path 但"不选"理由全写"业务不需要" —— 等于没决策
- 选 PTU 但 D2 硬约束栏"高吞吐 + 稳定 SLA"勾"否" —— 不一致，回去改 D2 或解释
- 部署选 Hosted Agents 但 D2 硬约束"私有部署"勾"是" —— 冲突，必走自托管
- 把"以后可能要 PTU"当作 PTU 选择理由 —— 决策按当前业务，未来留 risk register

## 兜底（Instructor宣布） / 兜底（讲师宣布）
- 90 min 内卡在 retry/cache 实操、来不及写完 decision note：**评审段口头讲清部署目标 + 容量模式 + 为什么不选其他**视为课堂验收通过；书面 note 课后 24h 内补交助教
