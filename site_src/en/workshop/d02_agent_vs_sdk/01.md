# D2-1: Architecture Overview and Capability Boundaries / D2-1: 架构总览与能力边界

> 时长：约 25 min ｜ 凭证：无 ｜ 类型：讲 + 速记

## Background / 背景
- D1 你定了"用不用 Foundry"，本步要在"用"这边再分叉：Agent Service / SDK / Workflows
- 三条路径不是替代关系，是承担不同职责；混合是常见解
- 本步是 D2 的概念基底，第 2/3 步要在这个基础上打分和算成本

## What You Need to Do / 你需要做什么
1. 跟讲师过一遍三条路径的职责分工，速记下表（填到自己笔记）：

   ```markdown
   | 路径 | 谁跑运行时 | 谁拥有状态 | portal 可见度 | 代码控制粒度 |
   |------|-----------|-----------|--------------|-------------|
   | Agent Service | | | | |
   | Agent Framework SDK | | | | |
   | Workflows | | | | |
   ```

2. 在表下方写 3 条边界判断（≥1 句话/条）：
   - "Agent Service 不擅长什么"
   - "SDK 不擅长什么"
   - "Workflows 不擅长什么"
3. 把 D1 决策卡里"部分用"对应的能力域（如果有）标到上面三条路径的某一条上

## Tips / 提示
- 三条路径不是技术对立，是"运行时归属 + 状态归属"两个轴上的不同点
- 如果你写"SDK 更灵活" —— 灵活不是边界，是修辞；要写"SDK 不擅长无人值班"这种具体的
- 速记是为了第 2 步的 4 维度打分有依据，不必追求精美

## Self-Check / 自检
- [ ] 三条路径职责表填完
- [ ] 3 条"不擅长"判断每条 ≥1 句具体场景
- [ ] 能说出"混合路径长什么样"（一句话举例）

## Submission (Counts Toward Capstone) / 提交（计入综合作业）
- 产物：上述职责表 + 3 条边界判断
- 放：`submissions/d2_1_overview/notes.md`

## Negative Examples / 反例
- "SDK 更灵活所以默认选 SDK" —— 灵活 ≠ 合适，自己负责运行时、状态、failover
- "选了 Service 就不能用 SDK" —— Foundry 支持混合，入口 agent 用 Service + 专家 agent 用 SDK
