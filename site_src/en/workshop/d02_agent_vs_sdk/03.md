# D2-3: Cost Estimation and Hybrid Path / D2-3: 成本估算与混合路径

> 时长：约 35 min ｜ 凭证：无 ｜ 类型：练 + 评审

## Background / 背景
- 第 2 步给了初步选择，本步要把"成本影响"算成具体数字，再决定要不要走"混合路径"
- 数字会回流到 D5（D5 spec 第一行就引用 D2 成本输入）
- 评审段讲师会抽人答："团队 6 个月后翻倍，这个决策要不要重做？"

## What You Need to Do / 你需要做什么
1. 在第 2 步的 `decision_card.md` 下方补上成本段：

   ```markdown
   ## 成本影响
   - Agent Service：托管费 + 平台调用费
   - SDK：自托管运行时（Container Apps / 自己 VM）+ 模型调用费

   ### 估算输入（必填，不接受"差不多"）
   | 项 | 值 |
   |----|----|
   | 日请求量（DAU × 人均次数） | _ |
   | 平均输入 token / 输出 token | _ / _ |
   | 并发峰值（QPS） | _ |
   | 是否需要 7×24 on-call | 是/否 |
   | 运行时规格（SDK 才填） | _ |

   ## 量级结论
   [哪一边总成本低，$/月 量级 + 主导成本项]

   ## 我没想清楚的地方
   [...]
   ```

2. 全部输入项必填，**不接受"差不多"**
3. 给出量级（如"Service ≈ $X/月，SDK ≈ $Y/月，主导成本项 = 模型费 / 容器费 / on-call 人力"），允许 ±50% 区间
4. 如果第 2 步选了 Service 但成本算出来 SDK 便宜很多（或反之），重新评估或显式写"为什么我仍坚持原选择"
5. 判断是否走混合：入口 agent 用 Service + 专家 agent 用 SDK 是否对你成本/运维更友好？

## Tips / 提示
- on-call 是 SDK 路径常被漏算的一项，按人力 $/月 估
- 量级正确比小数点正确重要 100 倍；不要纠结"是 $437 还是 $480"
- "我没想清楚的地方"写出来比假装确定得分高

## Self-Check / 自检
- [ ] 估算输入 5 项全填，无"差不多"
- [ ] 量级结论有具体数字方向 + 主导成本项
- [ ] 能口头回答："6 个月后团队翻倍，这个决策要不要重做？"
- [ ] 明确判断"走/不走混合"，理由 1 句

## Submission (Counts Toward Capstone) / 提交（计入综合作业）
- 产物：完整 `decision_card.md`（上下文 + 4 维打分 + 理由 + 成本段 + 混合判断）
- 放：`submissions/d2_3_cost/decision_card.md`（覆盖/合并 D2-2 的文件）

## Negative Examples / 反例
- "Agent Service 是托管的所以一定贵" —— 没算自托管 on-call
- 成本一栏写"差不多" —— 验收硬性不接受
- 选 SDK 但没人值班 —— 第一个 incident 把价差吃回来
